2. Why NDK r28b (28.1.13356709), and where the pins come from
----------------------------------------------------------------------

NDK r28b (28.1.13356709) is the version the Godot 4.7 documentation names (taken from the C1 brief, not re-read from the docs site here);
godot-cpp's own tools/android.py defaults `ndk_version` to the same "28.1.13356709". Google's manifest
https://dl.google.com/android/repository/repository2-3.xml (file sha256 f2bc624c8e1dc14c320fdf17e49a5501c35934948e46a444df8b36a138a03e1e
when it was read) says for that package:
package   : ndk;28.1.13356709 - NDK (Side by side) 28.1.13356709 (revision 28.1.13356709)
linux zip : android-ndk-r28b-linux.zip 722264879 bytes
sha1      : f574d3165405bd59ffc5edaadac02689075a729f (type sha1)
The script pins that size and SHA-1, plus the SHA-256 computed from the download once the SHA-1 matched (e9f27598...27ed). All three are
checked before anything is extracted. (r28c is 28.2.13676358; not used.)
Archive safety: the NDK zip holds 8,996 entries, 35 of them symlinks (clang -> clang-19, libc++.so.1 -> libc++.so, ...), so the S1 helper
that rejects every symlink cannot be used. assert_safe_zip_with_links (python3 -I, zipfile) requires: every entry below android-ndk-r28b/,
no absolute or '..' path, only regular files, directories and symlinks, each symlink relative with a target that stays inside the tree and
does not pass through another symlink, and no entry below a symlink. It passes the NDK zip and rejects the crafted archives below:
good -> exit 0 | 
abs_link -> exit 1 |   symlink with an absolute or empty target: top/l -> '/etc/passwd'
escape_link -> exit 1 |   symlink escapes top/: top/l -> ../etc
dotdot -> exit 1 |   unsafe path: 'top/../x'
outside -> exit 1 |   entry outside top/: 'other/x'
below_link -> exit 1 |   entry below a symlink: top/l/x
via_link -> exit 1 |   symlink target passes through another symlink: top/c -> top/a/x
abs_name -> exit 1 |   unsafe path: '/top/x'

6. NDK r28b and 16 KiB pages
----------------------------------------------------------------------

NDK r28b default LOAD alignment, trivial shared library, no -z max-page-size flag:
  aarch64-linux-android24      0x4000
  armv7a-linux-androideabi24   0x1000
  x86_64-linux-android24       0x4000
NDK r28b already links 64-bit Android libraries with 16 KiB LOAD alignment (0x4000) and 32-bit ARM with 4 KiB. native/SConstruct still passes
-Wl,-z,max-page-size=16384 for arm64 (and x86_64), so the result does not depend on the NDK default; 32-bit ARM keeps 0x1000 (armeabi-v7a does
not run on 16 KiB page-size kernels, and the Google Play requirement is for 64-bit libraries). The build checks the result with readelf
(build.txt) and tools/build_android.sh checks it again inside the APK (apk.txt).
